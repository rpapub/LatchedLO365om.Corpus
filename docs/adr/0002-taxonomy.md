# ADR 0002 — Taxonomy

**Status:** Accepted
**Date:** 2026-03-18

---

## Context

The corpus tooling introduces several concepts — scenario, fixture, label, manifest, workload,
expected — that overlap with general testing vocabulary but carry specific meanings here.
Without explicit definitions, the names are ambiguous across the yaml spec, the Python
package, and the UiPath test XAML.

---

## Decision

The following terms have precise, stable meanings within `cpmf-lo365om-corpus`.

---

### Scenario

A **scenario** is a self-contained test configuration declared in a single yaml file.
It specifies:
- which fixtures to create (the test data)
- what outcomes are expected per fixture (the oracle)
- how setup and teardown should behave
- which UiPath test cases belong to this scenario

A scenario is the unit of corpus setup. Running `setup` for a scenario creates exactly the
fixtures declared in that file and writes a manifest. Multiple scenario files may coexist;
each produces its own manifest.

A scenario is **not composable** — fixtures from one scenario yaml cannot be referenced in
another. This is a deliberate simplicity constraint.

---

### Workload

A **workload** identifies the M365 resource type being tested. Current values: `mail`.
Planned: `files` (SharePoint/OneDrive).

The workload determines which fixture types are valid (`fixtures.mail`, `fixtures.files`)
and which Graph API endpoints the setup script targets.

---

### Fixture

A **fixture** is a declaration of a single piece of test data to be created in the target
environment. For the `mail` workload, a fixture is a mail message with a subject, body,
importance, read state, and optional attachments.

Fixtures are **declarative** — they describe what should exist, not how to create it.
The setup script is responsible for creation.

Fixtures support **template variables** (`{run_id}`, `{label}`, `{date}`, etc.) that are
resolved at creation time. Values may also be **generated** (faker strategies).

---

### Label

A **label** is a stable, human-readable identifier for a fixture within a scenario.
Labels are `UPPER_SNAKE_CASE` strings (e.g. `MSG_FORM_BASIC`).

Labels serve three roles:
1. Key in the `fixtures` block — identifies the fixture declaration.
2. Key in the `expected` block — links the fixture to its expected outcomes.
3. Key in `corpus.json` — allows test XAML to look up the ImmutableId and expected values
   for a specific message by name.

Labels are stable across runs. ImmutableIds change every run.

---

### Manifest (`corpus.json`)

The **manifest** is the runtime test oracle. It is a JSON file generated by the setup script
after all fixtures have been created. It contains:
- `run_id` and `created_at` for traceability
- Per-label entries with: resolved ImmutableId, resolved field values, and the full
  `expected` block from the scenario yaml

Test XAML **reads only the manifest** — never the scenario yaml. This is the strict boundary
between generation (Python) and assertion (UiPath).

---

### Expected

The **expected** block in a scenario yaml declares the intended observable outcomes for each
fixture across all test cases that reference it. It uses **free-form string keys**
(e.g. `retrieval`, `bodyExtraction`, `eml`, `attachments`, `move_to_processed`) to group
related assertions.

Soft conventions for key names:

| Key | Covers |
|---|---|
| `retrieval` | Properties readable from the Graph message object (isRead, importance, hasAttachments) |
| `bodyExtraction` | BodyFieldExtractor output (values, unmatchedFields, missingRequiredKeys) |
| `eml` | SaveAllAsEml output (fileCount, minSizeBytes) |
| `attachments` | SaveAllAttachments output (count, minSizeBytes) |
| `move_*` | MoveMessage target folder expectations |

A test XAML reads only the key(s) it cares about. Unknown keys in the manifest are ignored.

---

### pytest Analogy

For readers familiar with pytest, the mapping is:

| pytest | This tooling |
|---|---|
| `conftest.py` (session scope) | `corpus_setup.py` / `Setup.xaml` |
| Fixture object in memory | Entry in `corpus.json` (ImmutableId + expected) |
| `@pytest.fixture(scope="session")` | Corpus message created once, reused across test cases |
| `expected` dict in fixture | `expected` block per label in `corpus.json` |
| `os.environ` overrides | `CORPUS_TOKEN`, `CORPUS_MAILBOX` env vars |
| `--scenario` CLI flag | `--corpus` path to scenario yaml |

The critical difference: pytest fixtures live in memory; corpus fixtures live in M365.
The manifest is the bridge — it externalises fixture state so UiPath can read it.

---

## Consequences

- Yaml authors use labels as the primary cross-reference mechanism.
- Test XAML authors look up fixtures by label from the manifest, never by position or subject.
- The `expected` block is intentionally free-form — new test cases can add new keys without
  changing the schema or breaking existing test cases.
- Adding a new workload (e.g. `files`) requires extending the taxonomy with new fixture types
  and manifest shape, but the core concepts (scenario, label, manifest, expected) remain
  unchanged.
